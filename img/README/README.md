# 2.3.1 POSIX API 与网络协议栈

这篇笔记围绕一个问题展开：**应用程序调用 socket API 后，内核怎样完成 TCP 的建连、传输和关闭？**

## 一、先建立整体关系：应用、API、系统调用、协议栈

在通常的 Linux 网络程序中，应用通过 socket API 请求内核进行网络通信：

```text
应用程序：C 网络程序、WebServer、各种语言的网络库
    ↓ 调用
socket / bind / listen / connect / accept / send / recv / close
    ↓ 经由库函数封装和系统调用进入内核
内核 socket 层与 TCP/IP 协议栈
    ↓
网卡驱动与网卡
    ↓
网络中的另一台机器
```

几个概念分别回答不同的问题：

| 概念                | 回答的问题                                   |
| ------------------- | -------------------------------------------- |
| POSIX API           | 应用能调用哪些函数、这些函数分别做什么？     |
| 系统调用（syscall） | 应用怎样请求内核服务？                       |
| TCP/IP 协议栈       | 怎样处理报文、维护连接状态、确认和重传数据？ |
| 网卡与驱动          | 怎样实际收发链路上的数据？                   |

例如，应用调用 `connect()` 请求建立连接；接下来发送 SYN、处理 SYN+ACK、发送 ACK，由内核 TCP 协议栈完成。应用虽然只调用一次函数，内核之后还会继续收发数据包、检查是否超时。

Java、Python、Go 等语言的常规网络库，在 Linux 上也会使用操作系统提供的 socket 能力。不过，“所有语言、所有平台都使用同一套 POSIX 调用”说得过满：其他系统有自己的接口，也存在用户态协议栈。

**这一章先记住：应用调用了函数、内核完成了某一步 TCP 处理、对端程序处理完了业务，是三件不同的事。**

## 二、fd、socket 和 TCB 分别是什么

### 2.1 fd：应用访问内核对象的入口

```c
int sockfd = socket(AF_INET, SOCK_STREAM, 0);
if (sockfd < 0) {
    perror("socket");
}
```

这里创建的是 IPv4 TCP socket。成功返回的 `sockfd` 是当前进程中的一个非负整数编号。程序把这个编号交给内核，内核就能找到对应的 socket。保存这些编号的表叫作“文件描述符表”。

fd 本身只是编号，不保存连接的全部信息；不同进程即使有相同的 fd 数字，也不一定指向同一个 socket。`socket()` 创建一个用来收发网络数据的对象，但此时还没有和对方建立 TCP 连接。[socket(2)](https://man7.org/linux/man-pages/man2/socket.2.html)

### 2.2 socket：通信端点

socket 可以理解为操作系统提供给程序的一个网络通信对象。监听 socket 用来等客户端连接，连接 socket 用来和某个已经连上的客户端收发数据。

服务端通常有两类 fd：

```text
listenfd：引用监听 socket，持续接收新连接
connfd：引用某一条连接的 socket，用于 send / recv
```

客户端传入 `connect()` 的那个 socket，在连接成功后用于通信；服务端则通过 `accept()` 获得用于这条连接的新 fd。

### 2.3 TCB：协议栈维护的 TCP 状态

TCB 叫作 TCP 控制块（Transmission Control Block），可以先理解为内核给 TCP 保存的一份“连接记录”，例如：

- 本地地址、对端地址、端口。
- `LISTEN`、`SYN_SENT`、`ESTABLISHED` 等连接状态。
- 发送序号、接收序号、确认进度。
- 收发缓冲区、窗口、重传定时器等信息。

监听点还需要管理连接请求和等待应用接收的连接。

也就是说，程序给出 fd，内核就能找到对应 socket，以及它保存的 TCP 信息：

```text
fd → 内核 socket 相关对象 → TCP 状态与缓冲区
```

Linux 实际上会用几种不同的数据结构保存这些信息。握手还没完成时，可能只先记下少量请求信息；所以不用把图里的 TCB 想成 Linux 中始终只有一个固定的 `struct tcb`，也不用认为每收到 SYN 就立刻创建一份完整的连接记录。

### 2.4 四元组、五元组与序列号的分工

讨论同一个网络环境中的 TCP 连接时，通常用下面四项信息区分不同连接，这四项合起来叫“四元组”：

```text
本地 IP、本地端口、对端 IP、对端端口
```

把协议类型也写进去，就是五元组。监听 socket 还没有固定对端，不具备某条已建立连接那样的完整对端信息。

**四元组用于区分连接，TCP 序列号用于描述连接中数据的位置。两者用途不同。**

## 三、先把常用 API 放到一条流程里

```text
服务端应用                             客户端应用
socket()                               socket()
bind()                                 [按需 bind()]
listen()                               connect()
    │                                      │
    └──────── 两端内核完成三次握手 ──────────┘
accept() → 获得 connfd                  connect() 成功
recv() / send()                         send() / recv()
close(connfd)                           close(sockfd)

服务端 listenfd 可以继续接受其他连接。
```

这张图表示职责关系。`accept()` 也可以提前调用并阻塞等待；它不要求应用先判断握手已经完成。客户端 `connect()` 成功返回与服务端应用 `accept()` 返回，也没有必须同时发生的关系。

| API          | 主要作用                    | 注意点                                  |
| ------------ | --------------------------- | --------------------------------------- |
| `socket()`   | 创建网络通信对象，返回 fd   | 创建 socket 不等于建立 TCP 连接         |
| `bind()`     | 绑定本地地址和端口          | 不触发握手；绑定端口 0 可由内核选端口   |
| `listen()`   | 把 socket 变成监听 socket   | 为接收连接请求做好准备                  |
| `connect()`  | 主动发起连接                | 让内核主动发起三次握手                  |
| `accept()`   | 接收等待中的连接，返回新 fd | 原监听 fd 继续监听                      |
| `send()`     | 向 socket 提交待发送字节    | 返回值不证明对端业务处理完成            |
| `recv()`     | 从 socket 取出接收字节      | 一次读取不对应一条应用消息              |
| `shutdown()` | 关闭连接的一个或两个方向    | 可以只关闭发送方向                      |
| `close()`    | 释放当前 fd                 | fd 释放后，内核可能还要继续完成关闭过程 |

## 四、连接建立：listen、connect、三次握手、accept

### 4.1 服务端：socket → bind → listen

`bind()` 指定本地 IP 和端口。IP 可以是具体接口地址，也可以是通配地址；它不表示某个客户端已经连上来

```c
listen(listenfd, 128);
```

`listen()` 把 socket 设成等待客户端连接的状态。之后有连接请求发到对应 IP 和端口时，内核就会处理，并把等待中的连接管理起来。[listen(2)](https://man7.org/linux/man-pages/man2/listen.2.html)

### 4.2 客户端：connect 触发主动建连

```c
connect(sockfd, server_addr, addrlen);
```

客户端提供对端地址。如果之前没有显式绑定本地地址，内核会在普通连接流程中选择适当的本地地址和临时端口，然后发起握手。

- **阻塞 socket**：调用 connect 后会等连接结果；成功返回 `0`，失败返回 `-1`，具体原因保存在 `errno` 中。
- **非阻塞 socket**：不用一直等在 connect 这里。它可能立即成功，也可能返回 `-1` 且 `errno == EINPROGRESS`，意思是“连接还在进行中”，不是已经确定失败。

非阻塞连接通常先等系统通知这个 socket 已经可以尝试写入，再用 `getsockopt(..., SO_ERROR, ...)` 检查连接结果。收到可写通知时，连接可能成功，也可能失败，所以还要做这一步检查。

### 4.3 三次握手交换什么

先看 TCP 数据包开头的字段图。`Sequence Number` 是序列号，表示发送数据的位置；`Acknowledgment Number` 是确认号，表示接下来期望收到的位置。SYN 用于发起建连，ACK 表示确认，FIN 表示这一方向的数据发送结束：

设客户端初始序号为 `c`，服务端初始序号为 `d`，本例握手报文不携带应用数据：

```text
客户端                                        服务端
CLOSED                                        LISTEN
   │                                             │
   │ SYN, seq=c                                  │
   ├────────────────────────────────────────────>│
SYN_SENT                                      SYN_RECEIVED
   │                                             │
   │                 SYN+ACK, seq=d, ack=c+1     │
   │<────────────────────────────────────────────┤
   │                                             │
   │ ACK, seq=c+1, ack=d+1                        │
   ├────────────────────────────────────────────>│
ESTABLISHED                                   ESTABLISHED
```

客户端收到并检查 SYN+ACK、发出最后 ACK 后，进入 `ESTABLISHED`（连接已建立）；服务端收到并检查这个 ACK 后，也进入 `ESTABLISHED`。因此，两端进入已建立状态的时间有先后。

SYN 占用一个序号，因此确认客户端 SYN 时是 `ack=c+1`；确认服务端 SYN 时是 `ack=d+1`。纯 ACK 本身不占用序号。

三次握手让双方知道对方从哪个序号开始发送，并确认双方都能收发数据，之后才能据此检查序号、确认数据和处理重传。服务端用来等新连接的监听 socket 仍然保持 `LISTEN`，进入已建立状态的是这个客户端对应的那条连接。

### 4.4 半连接队列与全连接队列

先用普通流程建立模型：

```text
SYN 到达监听端点
    ↓
内核记录握手请求，回复 SYN+ACK
    ↓
半连接：等待最后 ACK，通常处于 SYN_RECEIVED
    ↓ 收到并验证最后 ACK
连接完成握手，进入等待 accept 的队列
    ↓
应用 accept()，取得新连接的 fd
```

![原笔记中的三次握手与连接队列示意](https://camo.githubusercontent.com/9eae996a739845eeea18ed1bfb2e7b92fd2d2393be6ade06b0b2abde42d1e5f6/68747470733a2f2f63646e2e6a7364656c6976722e6e65742f67682f6c697869616f7a68656e67343231312f626c6f672d696d6167657340316565613531636564343633613931636237643333326631376335343963333637393131653930612f696d672f524541444d452f6d76727377316e672e706e67)

| 队列                      | 保存什么                       | 应用通过 accept 取得了吗？ |
| ------------------------- | ------------------------------ | -------------------------- |
| 半连接队列（SYN 队列）    | 尚未完成握手的请求状态         | 没有                       |
| 全连接队列（accept 队列） | 已完成握手、等待应用接收的连接 | 还没有                     |

可以先把这个过程想成“从半连接队列移到全连接队列”。实际实现中，内核可能先只保存少量握手信息，握手完成后再创建完整的连接记录。启用 SYN cookies（把部分握手信息编码到服务端序号中）时，处理方式还会不同。

**完成握手与应用拿到 fd 是两件事：连接可以先在内核建立，再等待应用调用 `accept()`。**

### 4.5 accept 返回之后，应用还要干什么

```c
int connfd = accept(listenfd, NULL, NULL);
```

在普通 TCP 流程中，`accept()` 取出已经完成握手、等待程序处理的连接，并返回一个新 fd。没有连接可取时，阻塞方式会继续等；非阻塞方式通常返回 `EAGAIN` 或 `EWOULDBLOCK`，意思是“现在暂时没有连接可取”。[accept(2)](https://man7.org/linux/man-pages/man2/accept.2.html)

在 Reactor（先等事件通知，再调用相应函数处理）模型中，后续工作通常是：

1. 获得 `connfd`，设为非阻塞，让后面的读写不必一直停在某个函数里等。
2. 程序自己保存一份连接信息，记录待发送的数据、已读到的数据、消息处理到哪一步等。
3. 把 `connfd` 加入 epoll 监听，让系统有数据可读时通知程序；需要等待继续发送时，也关注写事件。
4. 收到事件通知后，在对应的处理函数中调用 `recv()` / `send()`，读懂请求并回复数据。
5. 通信结束或出错时，清理连接对象并释放 fd。

这里有两份不同的记录：应用自己保存的连接信息用于处理业务；内核 TCB 保存的信息用于管理 TCP 连接和传输。

### 4.6 epoll、LT、ET 与 accept 的关系

`epoll` 是 Linux 的事件通知接口，**不负责替应用调用 `accept()`**。

对于监听 socket，`EPOLLIN` 通常表示“现在有新连接可以 accept”；对于已经用来通信的 socket，它可能表示“有数据可读”，也可能表示读完已有数据后能读到 EOF（对方已正常结束发送）。同一个事件，要看它来自哪种 socket。

| 模式         | 对监听 socket 的理解                                                   | 常见处理方式                                            |
| ------------ | ---------------------------------------------------------------------- | ------------------------------------------------------- |
| LT，水平触发 | 只要还有连接没 accept，就一直处于有连接可取的状态                      | 可以逐次接收，也常循环处理                              |
| ET，边沿触发 | 从没有连接可取变为有连接可取时会通知，不能指望没取完的连接一直重复提醒 | 监听 fd 设为非阻塞，循环 accept 到 `EAGAIN/EWOULDBLOCK` |

ET 中的基本流程是：收到监听 fd 的通知 → 循环 `accept()` → 每次成功就保存并处理新 fd → 直到暂时没有连接可取，再结束循环。`EINTR` 表示这次调用被信号打断，通常重试；其他错误按具体原因处理。

Linux 中，即使监听 fd 已设为非阻塞，`accept()` 返回的新 fd 也不一定自动沿用这个设置。新 fd 要另外设置 `O_NONBLOCK`，或者用 `accept4(..., SOCK_NONBLOCK)` 创建。这里设置的是**新 fd**；监听 fd 本身也要提前设为非阻塞。[accept(2)](https://man7.org/linux/man-pages/man2/accept.2.html) [epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html)

也不必固定记成“下一次 Reactor 循环才 accept”：要看通知什么时候到，以及程序什么时候处理它。

## 五、建连疑问：生命周期、请求匹配、SYN flood 与 backlog

### 5.1 TCP 连接的生命周期从什么时候开始

“从什么时候开始、什么时候结束”，要看说的是哪一件事：

| 层面           | 起止点怎样理解                                          |
| -------------- | ------------------------------------------------------- |
| 应用 fd        | `socket()` / `accept()` 获得 fd，到 `close()` 释放该 fd |
| TCP 建连尝试   | 主动端发起 SYN，或被动端开始处理某个连接请求            |
| 已建立连接阶段 | 连接进入 `ESTABLISHED`（已建立）后，可以正常传输数据    |
| 内核协议状态   | 关闭后还可能存在 `FIN_WAIT_*`、`TIME_WAIT` 等状态       |

所以，“调用 socket 就建立 TCP 连接”和“调用 close 后内核马上不再保存任何状态”都不准确。

### 5.2 第三次握手的 ACK 怎样找到对应请求

收到的数据包中带有发送方和接收方的 IP、端口。内核用这几项信息找到对应的连接或握手请求记录，再检查 ACK、序号等内容是否正确。

重点是：**内核根据 IP、端口和已保存的连接信息查找，不是根据应用的 fd，也不只看 ACK 数字。** 同一个监听端口可以对应许多不同客户端的连接。

使用 SYN cookies 时，内核可以根据最后一个 ACK 中带回的信息，检查握手是否正确，并重新得到连接所需的信息，不一定要提前保存普通的半连接记录。

### 5.3 SYN flood 为什么会造成压力

普通握手中，服务端收到 SYN 后会保存相关请求信息，还可能需要重发 SYN+ACK。SYN flood 就是大量发起这类请求却不完成握手，持续占用队列和内核的处理能力，影响正常客户端连接。

Linux 的 SYN cookies 可以缓解这种压力，但服务器收到的连接请求太多时，仍可能因为其他资源不足而处理不过来。

### 5.4 listen 的 backlog 究竟限制什么

在现代 Linux TCP 中，`backlog` 主要设置**已经完成握手、等待 accept 的队列最多能放多少条连接**。系统还会用 `net.core.somaxconn` 限制这个数值。半连接队列另有相关设置 `net.ipv4.tcp_max_syn_backlog`，它和全连接队列是两回事。

Linux 从 2.2 开始改变了 `backlog` 的含义。原笔记列出的“半连接队列、两个队列总和、全连接队列”不能直接当作 Linux 的三个确定历史版本；不同系统和历史实现需分别查证。[listen(2) 的历史说明](https://man7.org/linux/man-pages/man2/listen.2.html#NOTES)

增大 `backlog`，主要是给短时间内集中到来、程序还来不及 `accept()` 的连接多留一些等待位置。**它不会直接让程序处理业务更快，也不是程序已经接收的连接总数上限。** 如果一直不取队列里的连接，容量再大也会放满。

面试时可以这样回答：

> 在现代 Linux TCP 中，backlog 主要控制等待 accept 的已完成连接队列长度，并受到 somaxconn 的限制。它用于暂存短时间内集中到来的连接请求，不能直接当作服务器最多能同时维持的连接数。

## 六、数据收发：send、recv 与应用消息

### 6.1 send 成功表示什么

对普通 TCP `send()`，可以这样理解：

```text
应用缓冲区 → 本地内核发送缓冲 → TCP/IP 处理与网络发送
```

成功返回 `n > 0`，表示本次有 `n` 个字节交给了本地内核，等待发送。通常会把这些字节从应用缓冲区复制到内核缓冲区；看返回值时，先关注“这次交过去了多少字节”。

这不等于对方程序已经读到，也不等于对方处理完业务或把数据写入文件。一次 `send()` 还可能只交过去一部分数据，程序要根据返回的字节数，从剩下的位置继续发送。[send(2)](https://man7.org/linux/man-pages/man2/send.2.html)

### 6.2 recv 返回值怎样理解

普通接收路径是：

```text
网卡收包 → 内核协议栈处理与重组 → socket 接收缓冲 → 应用缓冲区
```

对请求长度大于 0 的 TCP `recv()`：

| 返回结果                   | 含义                                           |
| -------------------------- | ---------------------------------------------- |
| `n > 0`                    | 本次读到 n 个字节                              |
| `0`                        | 对端正常关闭发送方向，且此前数据已读完，即 EOF |
| `-1`，`EAGAIN/EWOULDBLOCK` | 非阻塞读取时暂时没有可读数据                   |
| `-1`，其他错误             | 按 `errno` 判断，例如连接重置                  |

如果接收缓冲区还有对端关闭前发来的数据，应先读到这些数据，之后才读到 EOF。因此不能写成“FIN 一到，recv 立刻返回 0”。[recv(2)](https://man7.org/linux/man-pages/man2/recv.2.html)

### 6.3 TCP 是字节流，消息边界由应用定义

发送端连续调用：

```text
send("hello")
send("world")
```

接收端可能一次读到 `helloworld`，也可能分几次读到。TCP 不保证一次 `send()` 对应一次 `recv()`。

所谓“粘包、拆包”，需要应用协议用固定长度、长度字段、分隔符等规则处理。这不是 TCP 把数据传错了。[tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)

还要分清三层进度：

```text
本地 send 返回 → 对端 TCP 确认 → 对端应用读取并处理
```

它们之间没有“前一个发生，就证明后一个完成”的保证。TCP ACK 也不能替代业务确认。

## 七、把 TCP 传输机制按“解决什么问题”重新分类

原笔记把慢启动、拥塞控制、滑动窗口、延迟确认和超时重传都列在了可靠传输下面。它们都影响传输，但各自解决的问题不同：

| 要解决的问题                                 | 主要机制                                          |
| -------------------------------------------- | ------------------------------------------------- |
| 数据处于什么位置，怎样按序交付、识别重复？   | 给字节编号、把乱序数据排好、识别重复数据          |
| 哪些数据已经收到，丢失后怎样恢复？           | ACK、SACK（补充说明哪些乱序数据也收到了）、重传等 |
| 接收方还有多少接收能力？                     | 接收窗口 `rwnd`，即流量控制                       |
| 网络还能承受多少已经发出、尚未被确认的数据？ | 拥塞窗口 `cwnd`，即拥塞控制                       |
| 什么时候发确认以减少报文开销？               | 延迟确认等 ACK 策略                               |

TCP 通过确认、重传等办法，让对方程序按顺序、无重复地读到字节数据。但如果网络一直不通，或者对方一直无法正常工作，连接仍会失败，不会无限重试并保证最终成功。

### 7.1 序列号与累计确认：确认的是字节位置

TCP 给字节流编号。`seq` 通常表示本段第一个数据字节的位置；`ack` 表示接收方**下一步期望按序收到的字节序号**，同时累计确认此前的字节。

例如，收到字节 `1000～1099` 后，下一步期望 `1100`，因此回复 `ack=1100`，不是 `ack=1099`。SYN 和 FIN 各占一个序号，纯 ACK 不占序号。[RFC 9293：序号与确认](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4)

所以原笔记中的“id 保证不重复、不乱序、不丢失”应展开为：序号用于定位字节、识别重复和组织顺序，再与确认、重传等机制配合提供可靠传输。并不是靠一个包 ID 就同时解决所有问题。

#### 用“收到 1、2、3、5”例子说明

为避免把段编号误当作 TCP 序号，设每段恰好承载 100 字节：

| 段  | 字节范围   | 接收情况           |
| --- | ---------- | ------------------ |
| 1   | 1000～1099 | 收到               |
| 2   | 1100～1199 | 收到               |
| 3   | 1200～1299 | 收到               |
| 4   | 1300～1399 | 缺失               |
| 5   | 1400～1499 | 收到，属于乱序数据 |

在缺口补齐前，累计确认仍然是：

```text
ack = 1300
含义：1300 之前已经连续收到，接下来还在等 1300。
```

如果接收方已经把第 5 段暂存下来，等第 4 段补齐，就连续收齐了 1000～1499，确认号也就可以增加到 `ack=1500`。

双方商定使用 SACK 后，接收方还能在 TCP 包的附加信息里告诉对方：“虽然中间有缺口，但 1400～1499 这段也收到了。”发送方就能据此选择缺失的数据重传。仅凭普通的累计 ACK，发送方不能直接知道后面哪些乱序数据也到了。[RFC 2018：SACK](https://www.rfc-editor.org/rfc/rfc2018.html)

**这个例子主要解释累计确认和乱序接收；加上 SACK 后，还能解释选择确认。它不是延迟确认的定义。**

### 7.2 滑动窗口：允许多少数据尚未确认

先站在发送方看，数据可以分成四类：

```text
已发送且已确认 | 已发送但未确认 | 窗口内尚可发送 | 窗口外暂不能发送
```

“已发送但未确认”包含多种可能：数据仍在途中、数据丢失、对方已经收到但 ACK 尚未到达，或 ACK 丢失。

因此，不能把它直接定义成“已收到未确认”，也不能仅凭没收到 ACK 就断定对端没收到数据。

ACK 确认了更多数据后，发送方就不用再保留这些已确认数据来等待重传，窗口的起点也移到后面的数据，可以继续发送。至于最多能发到哪里，还要看对方有多少接收空间，以及网络是否拥堵。

这里有两个不同的限制：

- `rwnd`（接收窗口）：接收方告诉发送方，自己还能接收多少数据。
- `cwnd`（拥塞窗口）：发送方根据网络情况，决定最多允许多少数据发出后还没得到确认。

下面公式里的“在途数据”指已经发出、但还没得到确认的数据。`min` 是取较小值，`max` 是取较大值。可以先按这个简化模型理解：

```text
允许在途数据量 ≈ min(rwnd, cwnd)
可再发送的新数据量 ≈ max(0, min(rwnd, cwnd) - 已发送未确认的数据量)
```

如果接收方程序一直不 `recv()`，内核用来暂存数据的接收缓冲区就可能放满。接收方告诉对方“我还能收多少”的数值会变小，甚至变成零，发送方就不能继续按原来的量发送。[RFC 5681：rwnd 与 cwnd](https://www.rfc-editor.org/rfc/rfc5681.html#section-2)

**滑动窗口让发送方可以连续发一批数据，不用每发一段就停下来等 ACK；同时，它限制还没得到确认的数据有多少。它的主要作用不是减少重传次数。**

### 7.3 延迟确认：决定什么时候发送 ACK

接收方按顺序收到数据后，有时可以稍等一下再回 ACK，把几段数据一起确认；如果自己也要发数据，还可以把 ACK 跟着数据一起发回去，减少单独发送确认包的次数。

不过不能一直等，也不是遇到乱序数据都要等。比如中间缺了一段时，及时回复当前确认号，有助于发送方更早发现缺失并重传。[RFC 5681：确认生成策略](https://www.rfc-editor.org/rfc/rfc5681.html#section-4.2)

把这三个概念分开记：

| 概念     | 回答的问题                                       |
| -------- | ------------------------------------------------ |
| 累计确认 | 连续收到了哪里？下一个期望字节是什么？           |
| 延迟确认 | 这个 ACK 什么时候发？                            |
| SACK     | 除了连续部分，还有哪些不连续的字节范围也收到了？ |

延迟确认的主要目标是减少 ACK 开销，不能把“少重传缺失范围以外的数据”直接归因于延迟确认。

### 7.4 超时重传：没等到确认时怎样恢复

发送方不能直接看到对方收到了没有，要通过 ACK 等回复判断哪些数据已经收到。如果等到超时还没有得到相应确认，就重传未确认的数据。

发送后等多久还没有确认，就需要重传，这个等待时长叫 **RTO（重传超时时间）**。它会根据数据发出去再收到确认所需的时间 **RTT（往返时间）**，以及这个时间的变化来调整。它不是数据包的“存活时间”，也不同于 IP 的 TTL（限制数据包经过多少次转发）。

可以这样建立基础模型：

1. 还有已发送、未确认的数据时，使用定时器计时，检查是否等得太久。
2. ACK 确认了更多数据时，调整计时；所有已发送数据都确认后，停止计时。
3. 超时时，重传最早还没被确认的那一段，并把下一次的等待时间加长，通常翻倍。这种重试时逐步延长等待时间的做法，叫作“指数退避”。

不要直接记成“每个包各自一个独立定时器，超时后整批重发”。[RFC 6298：RTO 与定时器管理](https://www.rfc-editor.org/rfc/rfc6298.html#section-5)

如果数据已经收到，但 ACK 丢失，发送方可能重传相同序号范围的数据；接收方通过序号识别重复，避免把同一批字节重复交付给应用，并反馈当前确认进度。

用前面例子的数字：若 `1000～1499` 已连续收到，接收方可以继续回复 `ack=1500`。不能把它写成 TCP 固定“回复第 5 个包的编号”。

TCP 也不一定每次都等到超时才重传；它还可以根据重复 ACK 等情况更早发现可能丢失的数据，这叫快速重传。

### 7.5 慢启动属于拥塞控制

慢启动、拥塞避免、快速重传和快速恢复，在经典 TCP 拥塞控制中彼此配合。慢启动不是和“拥塞控制”互不相关的另一套机制。

以经典的 Reno 拥塞控制算法为例，可以这样理解：

- **慢启动**：随着数据不断得到确认，逐步增大 `cwnd`。理想情况下，每经过一轮发送和确认，窗口接近翻倍，也就是近似指数增长。
- **拥塞避免**：窗口改成慢慢增加；在经典模型里，每经过一轮发送和确认，增加的量大致相同，也就是近似线性增长。
- **检测到丢包等情况**：按具体算法缩小或调整窗口，再逐步恢复发送。

这里说的增长，是允许有多少数据发出后暂时还没得到确认，也就是**拥塞窗口**变大；实际测到的发送速度不一定严格按翻倍或直线的方式增加。

“发现拥堵就把速率砍半，然后线性增长”不能概括所有情况。比如经典算法里，等到超时才发现问题，和收到重复 ACK 后发现问题，处理方式就不同；超时后通常会把窗口明显缩小，再重新慢启动。不同算法怎样增加和减少发送量，也不完全一样。

可以先这样记：**刚开始少发一些，逐步试出网络能承受多少；发现可能拥堵时，就减少发送。** 具体增减多少，要看使用的算法，以及是超时还是重复 ACK 等情况。

## 八、关闭连接：close、shutdown 与四次挥手

### 8.1 先理解 TCP 的两个方向

TCP 是全双工连接，也就是两端都能同时收发数据。FIN 表示：

> 我在这个方向的数据已经结束。

收到 FIN，不等于自己也必须立刻停止发送。两个方向分别结束，所以普通关闭过程通常画成四步；ACK 和 FIN 也可能合并，实际不一定正好四个报文。

“主动关闭方”可以是客户端，也可以是服务端。原状态图中的左右分支，应该先按主动、被动关闭理解，不能固定成左边永远是客户端、右边永远是服务端。

### 8.2 四次挥手与状态对应

以下假设 A 先发起关闭、B 随后关闭，双方正常通过 FIN 结束各自的发送方向：

| 步骤     | 报文与事件                             | A 的状态      | B 的状态      |
| -------- | -------------------------------------- | ------------- | ------------- |
| 初始     | 双方正常通信                           | `ESTABLISHED` | `ESTABLISHED` |
| 1        | A 发送 FIN；B 收到该 FIN               | `FIN_WAIT_1`  | `CLOSE_WAIT`  |
| 2        | B 确认 A 的 FIN；A 收到 ACK            | `FIN_WAIT_2`  | `CLOSE_WAIT`  |
| 3        | B 完成发送后发出 FIN；A 收到并回复 ACK | `TIME_WAIT`   | `LAST_ACK`    |
| 4        | B 收到最终 ACK                         | `TIME_WAIT`   | `CLOSED`      |
| 等待结束 | A 的 TIME_WAIT 计时结束                | `CLOSED`      | `CLOSED`      |

表中列的是每个关键报文被相应一端处理后，双方处于什么状态。如果发生丢包、双方同时关闭，或者用 RST 直接中止连接，状态变化还会不同。[RFC 9293：关闭连接](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)

### 8.3 close 和 shutdown 不能完全等同

- `close(fd)` 释放当前 fd。正常情况下，等没有其他 fd 或正在进行的操作继续使用这个 socket 时，内核会处理关闭；关闭报文的发送和最后的清理可能还要继续。
- `shutdown(fd, SHUT_WR)` 关闭发送方向，保留当前 fd 用于继续读取；这是表达“我发送完了，还要接收你的数据”的常见方式。

所以，“发出 FIN 后还能收数据”是 TCP 半关闭的能力；如果程序已经 `close(fd)`，就不能再用这个已释放的 fd 调用 `recv()`。

关闭连接也可能直接发送 RST，表示中止连接，不再走完整的 FIN 流程。四次挥手讲的是双方正常结束通信的情况。

### 8.4 CLOSE_WAIT：等待本地应用结束发送

`CLOSE_WAIT` 表示：已经收到对端 FIN，本地发送方向还没有关闭。此时应用可能确实还有响应需要发，因此短暂出现这个状态并不异常。

如果大量连接长时间停在 `CLOSE_WAIT`，重点检查：

- 读到 EOF（对方已正常结束发送）后，是否处理完业务，并关闭自己的发送方向、清理连接。
- 发生错误或超时时，有没有漏掉关闭和清理。
- 任务有没有一直卡住，是否还有其他 fd 或操作在使用这个 socket，导致它没有真正关闭。

`recv()==0` 表示对方已经发完了，但本地程序还需要自己决定接下来怎么做：如果还要回复数据，就发完再关闭；如果已经没有事情要做，就结束并清理。

### 8.5 TIME_WAIT：关闭后继续保留一段协议状态

正常关闭时，先发起关闭的一方回复最后一个 ACK 后，会进入 `TIME_WAIT` 等待一段时间。标准中用 `2MSL` 表示这个时长，MSL 指一个报文在网络中可能存活的最长时间。这样等待主要为了：

1. 对端若因最终 ACK 丢失而重传 FIN，本端仍能再次确认，帮助对端完成关闭。
2. 等旧连接里迟到的数据包在网络中消失，避免它们影响以后使用相同 IP 和端口组合建立的新连接。

应用可以已经 `close()` 了 fd，而内核仍保留 TIME_WAIT 这份连接记录。等待也不能保证最后 ACK 一定到达；它让内核在对方重发 FIN 时，还有机会再回复 ACK。

### 8.6 CLOSING：双方同时关闭

如果双方几乎同时发 FIN，而且自己的 FIN 还没得到确认，就先收到了对方 FIN，连接可能进入 `CLOSING`（双方都在关闭）。之后自己的 FIN 得到确认，再进入 `TIME_WAIT`。

所以“谁主动关，谁 TIME_WAIT”适合记普通单方主动关闭；同时关闭时，双方都可能进入 TIME_WAIT。

## 九、一条主线串起来

```text
socket：拿到一个通信端点和 fd
    ↓
bind / listen：服务端准备好接收连接
    ↓
connect：客户端发起建连
    ↓
两端 TCP 协议栈完成握手：同步序号、建立连接状态
    ↓
accept：服务端应用拿到这条连接的 fd
    ↓
send / recv：应用提交和读取字节流
    ↓
TCP 用序号、确认、重传、窗口和拥塞控制管理传输
    ↓
shutdown / close：应用推动关闭并释放资源
    ↓
TCP 状态机完成后续关闭与等待
```
